# 架构

## 产品形态

安册是单机、离线、无账号的敏感资料管理 App，面向中文用户整理自己和家人的资料。Android 是当前交付平台；iOS 不进入近期队列，也不构成平台交付承诺，既有平台无关边界保持。

## 设计取舍

- 资料保持单一成员归属，交互以「谁的资料」组织；系统家庭归属显示「全家共用」，不引入多人共同归属关系。
- 模板定义保存在代码中，不作为用户数据入库，不建设通用的在线配置或任意字段引擎。
- 数据库、附件和导出备份分别建立加密边界；本机密钥不进入备份，AppLock PIN 不作为数据库加密密钥。
- 搜索按当前个人／家庭规模读取低敏摘要，不保留完整字段预热缓存或依赖墙上时间的增量索引；尾号匹配只从数据库返回资料 ID，候选不在页面筛选前截断。
- 平台能力通过接口隔离，页面只负责展示和交互编排，业务规则放入 service/controller，持久化放入 repository。
- 进度与未决事项只放在 [路线图](../ROADMAP.md)，视觉约束放在 [视觉规范](ui-visual-design.md)，不另维护重复的全景说明或决策副本。

## 核心对象

`Item` 是核心对象，成员和类型只是访问资料的两个维度。

```text
Member 1 ── n Item 1 ── n ItemField
                  ├── n Attachment
                  ├── n Reminder
                  └── n ItemChildEntry 1 ── n ItemChildField
```

- `Member`：本人、全家共用和其他家庭成员；每条资料仍只归属一个成员维度。
- `Item`：一条证件、卡片、保险、车辆或其他资料。
- `ItemField`：模板定义的字段值。
- `Attachment`：保存在应用私有目录中的加密文件。
- `Reminder`：资料日期对应的提醒配置；当前仅完成数据结构和到期概览，尚未实现系统通知。
- `AppSettings`、`LicenseState`：设备本地状态，不等于账号。

## 模块边界

- `core/database`：Drift 表、迁移和数据库打开器。
- `core/repository`：数据访问与领域模型映射。
- `core/service`：校验、派生文本、搜索、到期计算和业务用例。
- `core/template`：代码内置的固定模板，不把模板配置持久化。
- `core/security`：密钥、AppLock、运行模式、重置和防窥策略。
- `core/backup`：备份载荷、加解密、导入导出及平台文件服务。
- `core` 同时容纳共享 UI 基础与对应能力的 Android 适配器；平台服务通过接口接入，业务规则不反向依赖页面。
- `features`：页面展示与页面级交互。
- `core/widgets`：与资料类型无关的通用布局和交互组件。
- `widgets`：跨页面资料卡片和详情入口；`card_contract` 保存展示模型、无状态摘要构建与搜索高亮，不持有资料缓存，也不依赖页面类型定义。
- `app/dependency_provider.dart`：依赖根；正式运行只能从这里共享同一个数据库实例。
- 录入导航由 `ItemEntryFlowPage.open` 接收编辑快照、成员或续保草稿并创建页面路由，沿用调用上下文的受保护导航器；依赖根只装配服务与 controller，不负责打开页面。
- `main.dart` 的 `AnchBootstrapRoot`：拥有一次完整应用会话的运行时、数据库和依赖树；物理清空本机资料后先移除旧子树，再创建新密钥、数据库和页面依赖。

批量字段迁移编排位于 `tool/migration_orchestrator.dart`，仅供隔离虚构资料的修复测试与性能基准调用，不进入应用运行依赖，也不作为真实资料维护入口。正常保存所需的字段转换仍由 `core/template/migration_service.dart` 提供；数据库 schema 升级、备份迁移和本机清空时的历史临时文件处理保持各自职责。

恢复页通过 `onSelectFile`、`onDecryptPreview`、`onApplyRestore` 等业务回调接入既有协调器，测试复用同一注入入口。历史临时验证输入保存在 `build/`，与当前应用源码分开；重新执行时创建适配当前接口的新输入，保留旧版本，默认静态检查不扫描构建产物目录。

## 数据流

新增或编辑资料：

```text
Page → ItemUseCaseService → validation / text builder → ItemRepository → Drift
```

读取资料：

```text
Page → Repository / Service → Drift → domain model → display model
```

页面不得直接实现加密、数据库迁移或模板业务规则。

成员和类型列表通过仓储查询条件在数据库内收窄范围，保留统一的置顶／更新时间排序；数据管理统计直接执行 COUNT，不构造资料模型。仓储列表统一返回低敏摘要，详情、编辑和备份继续使用各自的完整读取入口。

页面分别持有本地请求序号，只有最新请求且页面仍挂载时才能提交结果。首次读取失败显示明确的错误与重试；刷新失败保留上次内容并反馈，不冒充空资料，不保留跨页面全局数据缓存。

录入的动态字段增删重排、草稿字段输出和编辑值／来源还原由现有 `ItemEntryFlowController` 与 state 管理；必填校验、字段联动和身份资料建议也由 controller 处理，联动一次通知且保留用户已编辑字段及来源。页面持有输入与焦点控制器、导航和弹窗编排；文本、性别和日期／时间控件集中在现有 `item_entry_text_field.dart`，附件草稿继续沿用已有控制器。录入固定为「类型 → 归属 → 字段 → 补充」，成员入口可预选归属并跳过归属步骤；编辑和续保继续使用原资料的模板版本。类型选择与分类入口共用 `TemplateRegistry`，不维护独立任务定义或录入顺序开关。分类按已保存类型聚合，已停用类型仍可浏览，未知历史类型以「历史资料」入口保留访问。

详情的字段筛选、排序、分组、号码与户口成员渲染由现有 `ItemDetailFieldsSection` 负责；页面拥有显隐状态、复制确认、附件操作和安全生命周期，通过回调驱动字段展示。字段定义及历史安全兜底统一由 `TemplateRegistry.fieldDefinitionByKey` 提供，标题数据加工归入现有 `TitleSummaryBuilder`，不让复制流程依赖展示组件的静态规则。

首页、全部资料、成员、类型、归档、搜索和到期页共用 `ItemSummaryCard`；页面保留各自查询、筛选、刷新和长按操作。`AnchCardBuilder` 显式接收低敏摘要、成员名称与时间，输出不可变展示模型，没有注册、解析或缓存失效步骤，也不再生成测试专用 DTO 或经过旧展示合成器。测试直接检查实际卡片模型与渲染行为。最近删除使用带恢复／永久删除操作的专用行，不打开已删除资料详情。

「数据与备份」直接进入导出密码页或恢复文件选择页，不叠加备份菜单页。密码、系统文件交互、认证、覆盖确认、staging 与生命周期清理继续属于具体操作流程。

应用根节点直接消费 `AppLockBootstrapGate`。它将启动决策映射为配置恢复页或 `AppLockGate`，后者监听运行期锁定状态并覆盖整个内部导航器；不再叠加只转发参数的保护壳。

内部页面的业务弹窗显式使用当前导航器，随内部内容一起受应用锁门禁保护，不能放到门禁外的根导航器。已打开的确认弹窗在锁定期间不得接受复制、归档、删除或设置变更等操作；重新解锁后可继续原流程。恢复页进入后台还须主动关闭已认证清单，并在同一导航器中清理。PIN 找回及本机资料清空属于锁页上的认证／恢复流程，保留根层路由与各自确认，不能因业务弹窗收口而阻断。

物理清空本机资料会关闭当前数据库并删除数据库文件、附件、PIN 与本机密钥。完成删除后，页面只能请求应用根节点重建会话；不得继续刷新、导航或向旧 `DependencyProvider` 创建的仓储发起读取。根节点在新会话初始化完成前仅展示不可交互的重建状态，并对并发重建请求去重；新会话必须重新执行安全窗口、屏幕保护、密钥、数据库预热、系统成员补齐和应用锁初始化。

## 平台边界

领域模型、数据库、加密格式和页面应保持平台无关。以下能力必须通过接口适配：

- 备份文件选择和保存。
- 安全窗口或后台快照保护。
- 本机安全存储。
- 生物识别。
- 本地通知。

当前 Android 使用 SAF 和 `FLAG_SECURE`；仓库尚无 iOS 工程与对应实现。

屏幕内容保护由平台无关的三档偏好、前台敏感页面信号和应用生命周期共同决策，再通过安全窗口接口映射到 Android `FLAG_SECURE`。展示完整字段、附件明文或接收安全凭据的页面自行声明敏感范围，低敏摘要列表不依赖所在导航层级继承保护；页面不直接调用 MethodChannel。`inactive` 只表示通知栏、系统截图控件或其他系统浮层造成的短暂前台失焦，不单独视为进入后台；生命周期进入 `hidden／paused／detached` 时无条件请求保护，回到 `resumed` 后再恢复用户选择对应的策略。该偏好使用独立本机安全存储键，不写入业务数据库或备份载荷。

## 备份可靠性

当前默认导出使用流式 V3，历史 V1／V2 保留导入兼容。V3 的附件由备份密码保护，恢复时使用当前本机密钥重新加密；旧格式附件依赖原设备密钥，无法解密时在覆盖前拒绝。

流式恢复先认证 manifest 并展示受限清单，用户确认后才完整认证包体、准备附件 staging，再执行附件目录原子切换与数据库事务。持久化恢复日志与数据库提交标记协调跨资源中断；完整验证通过前不得覆盖当前数据。

格式、长度与来源校验、最终提交帧、进度、失败与会话清理的唯一详细规范见 [备份格式](backup-format.md)。独立 `:streaming_benchmark` 只验证虚构字节，不替代生产路径真机结论；操作方法见 [测试策略](testing.md)。

## 资料归档与保险续保

### 能力边界

归档用于保留已经不再日常使用、但仍可能需要查阅的历史资料。它是通用收纳能力，适用于已续保的旧保险、已注销银行卡、换发后的旧证件、已转让或报废的车辆资料等，不为保险单独建立复杂生命周期。

业务状态与收纳状态必须独立：

```text
业务状态：正常／即将到期／已过期／已注销等
收纳状态：当前／已归档
```

“已注销”描述资料是否仍可使用；“已归档”描述用户是否希望在日常列表和提醒中继续看到。标记注销、过期或续保后不得自动归档，必须由用户确认，避免刚处理的资料突然消失。

### 归档行为

- 当前资料出现在首页、成员、类型、搜索和到期提醒中；已归档资料从这些默认入口排除，也不计入默认资料数量和需要关注数量。
- 已归档资料的字段、附件、业务状态和操作记录完整保留，不等于删除。
- 在“全部资料”提供轻量“已归档”入口或筛选，在“数据与备份”提供带数量的“已归档资料”入口；归档列表支持查看详情、编辑和恢复到资料列表。
- 默认搜索不混入已归档资料；归档中存在匹配时，应提示匹配数量并允许用户主动查看。
- 从归档恢复后，原业务状态不改变。例如已注销银行卡恢复到列表后仍是“已注销”，不会重新变成可用卡。
- 归档资料允许移入最近删除；从最近删除恢复时必须回到删除前的收纳状态，不得把原已归档资料错误恢复为当前资料。
- 归档时取消置顶，恢复到当前资料后不自动恢复原置顶，避免资料未经再次确认就回到首页顶部。
- 归档、取消归档、移入最近删除和恢复必须与对应操作记录在同一事务内提交或回滚；归档和取消归档使用明确事件类型，不由界面从普通更新事件猜测动作。
- 归档、恢复、备份和导入不得丢失附件、业务状态、删除前收纳状态或操作记录；实现前必须全局审计首页、成员、类型、全部资料、数量、搜索、到期提醒、置顶、备份预检和详情跳转的状态过滤。

交互统一使用“归档资料”“取消归档”和“已归档资料”，避免“收起”与界面折叠混淆。归档前说明资料仍会保留且可找回；成功后提供短时撤销入口。已归档详情不隐藏编辑、续保和移入最近删除能力。

V8 已为归档／取消归档增加明确事件类型，并为删除中的资料保存删除前 `active／archived` 收纳状态。历史已删除资料升级时按既有行为视为从当前资料删除。资料状态、事件和删除前状态在同一事务内提交；非法组合由表约束与备份载荷校验共同拒绝。

### 保险续保

保险续保按是否形成新合同或新保障期处理：

- 同一长期合同继续缴费或修正信息：编辑现有资料。
- 产生新保单号、新保障期间或新保单文件：使用“续保一份”，复制稳定字段并创建新资料，不覆盖旧保单。

“续保一份”只带入归属成员、保险公司、保单名称、险种、投保人、被保险人和客服电话；不复制置顶状态、操作记录或原资料标识。保单号、保障日期、保费、保额、备注和附件必须清空，并停留在完整编辑流程供用户确认。取消编辑或保存失败时，来源资料不得发生变化。

来源可以是当前保险或已归档保险。当前保险的新资料保存成功后，显示不可点击遮罩跳过的明确选择：“归档上一份”或“暂不归档”；不得自动归档。归档上一份失败时保留已经成功创建的新资料，明确提示失败并允许稍后处理，不回滚新资料。来源已经归档时不重复询问。完成选择后进入新资料详情。

第一版不建立上一份／下一份保单关系链，也不引入 `current／renewed／terminated／lapsed` 等保险专属状态。旧保单是否停止提醒只由用户是否归档决定：

```text
已过期＋当前：继续展示并提醒
已过期＋已归档：保留历史，不再展示和提醒
```

### V8 数据结构变更审计

- 数据库版本从 V7 升至 V8；`item_events.event_type` 增加 `archived` 和 `unarchived`，不以普通更新事件代替归档动作。
- `items.status_before_deletion` 只允许 `active／archived`，且仅 `deleted` 资料必须具有该值；删除时间与删除前状态均通过表约束和事务保持一致。
- 当前或归档资料移入最近删除时保存原收纳状态并取消置顶；恢复时读取该状态并清空删除字段，不恢复历史置顶。
- V1～V7 数据库均可升级至 V8；历史删除资料的删除前状态补为 `active`，不伪造归档历史。
- 备份载荷保留删除前状态和两种新事件；旧 schema 载荷迁移时补齐历史删除来源，当前载荷拒绝缺失、非法或与资料状态冲突的组合。

## 详情操作记录与最近删除

操作记录是资料生命周期事件与低敏变更摘要，不是资料版本、撤销快照或合规审计日志。主事件记录资料 ID、动作类型和发生时间；变更摘要只允许保存归属成员、分类、类型、状态、置顶等结构变化，以及敏感等级为 none／low 的日期类字段新旧值。标题、备注、普通文本和中高敏字段只记录字段名称，不复制旧值或新值；附件只记录添加和移除数量，不保存名称、内容或路径。

资料事件由业务事务写入数据库，不由页面在成功回调后补记。资料变更与事件必须同事务提交或回滚，详情只查询当前资料的事件。资料存续期间完整保留事件，不以 UI 展示数量作为数据删除上限；详情可按需分批读取。永久删除资料时通过外键级联清除其事件。

普通删除改为软删除：资料状态切换为 `deleted`，记录删除时间并取消置顶，字段、子项和加密附件继续保留。首页、成员、分类、搜索和到期概览只读取活跃资料；删除后的查看和恢复统一位于“数据与备份”的“最近删除”，不得借用其他资料详情展示恢复入口。永久删除必须再次确认，并采用可补偿的附件文件清理流程。

资料事件及其变更摘要随加密备份导出和覆盖恢复，避免恢复后再次丢失历史。旧备份没有事件或变更摘要时按空列表迁移，不伪造历史记录；恢复前必须拒绝缺失引用、未知类型、非法值结构，以及试图为不允许字段恢复历史值的载荷。备份、清除本机资料等应用级动作不批量写为每条资料的详情事件。未来家人间传资料不携带发送方操作记录，接收方导入事件在该功能设计时另行定义。

操作记录可以解释低敏结构和日期变化，但不保存完整字段版本，也不得作为合规或安全审计证据。正式运行时事件、变更摘要与资料共同受加密数据库保护。

### V6 数据结构变更审计

- 数据库版本从 V5 升至 V6；新增按资料外键关联的事件表，替代全局内存最近 3 条队列。
- `items` 从仅有无约束状态字段，改为增加删除时间、状态枚举约束，以及“删除状态必须与删除时间同时成立”的表级约束；增加状态与删除时间联合索引。
- `item_fields` 移除运行时已不读写的 `template_field_known`、`is_archived_field` 和 `archived_reason`，保留恢复兼容仍需要的 `raw_field_label`。
- `attachments.status` 从无约束文本改为只允许 `active` 和 `deleted`。
- `metadata.raw_state` 从重复保存标题、备注和字段明文，改为迁移时清理且新保存不再写入；正式字段表成为资料值唯一来源，诊断、字段来源和低敏派生信息继续保留在 metadata。
- V1～V5 升级时先规范化非法状态，再安全重建相关表；历史 `deleted` 资料使用原更新时间补删除时间。升级失败必须回滚，成功后执行外键完整性检查。
- 旧全局内存记录管理器、快照和模型在运行时与测试解除引用后删除，不保留兼容层或双写路径。

### V7 数据结构变更审计

- 数据库版本从 V6 升至 V7；新增 `item_event_changes`，通过事件外键级联关联 `item_events`，替代“更新事件没有具体说明”的结构。
- 变更明细由 `change_kind`、稳定主题 key、展示标签、受策略控制的新旧值和排序组成；表级约束保证字段名称型变更不得携带值，值变化和附件数量变化必须同时具有旧值与新值。
- 资料保存由“每次保存只写 updated”改为“事务内比较修改前后状态，仅在存在实际业务差异时写 updated 及明细”；置顶、移入最近删除和恢复也在各自事务中写入结构化状态变化。
- 普通／中高敏字段由“没有差异说明”改为“只记录字段名称”；仅 none／low 日期字段和成员、分类、类型、状态、置顶等结构变化允许保存新旧展示值；附件由文件信息改为只记录添加／移除数量。
- 加密备份新增可选的事件变更明细集合；旧备份缺少该集合时读取为空，恢复校验拒绝高敏历史值、未知变更类型、重复 ID 和缺失事件引用。
- V1～V5 仍执行原 V6 规范化迁移后创建变更明细表，V6 直接创建新表；所有历史版本升级均不伪造字段差异。

## 规模假设

目标是个人或家庭的数十到数百条资料，而不是大型文档库。优先保证安全、正确和简单；只有基准证明必要时才引入索引缓存、分块和额外抽象。
